# VyapaarSaathi — Backend

FastAPI backend for the iQOO Hackathon 2026 project. Implements the 6
documented endpoints the Flutter frontend already calls, backed by real
SQLite storage, real OCR (Tesseract), real speech-to-text (faster-whisper),
and real PDF generation (reportlab) — not stubs.

Every endpoint below was actually run and tested against real requests
during development, not just written and assumed correct. Results and
gotchas from that testing are documented here, not hidden.

---

## 1. Setup

```bash
# System dependency — pytesseract wraps this binary, doesn't include it:
sudo apt-get install tesseract-ocr   # Ubuntu/Debian
# brew install tesseract             # macOS

pip install -r requirements.txt

python3 main.py
# or: uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

Visit `http://localhost:8000/docs` for interactive Swagger docs
(auto-generated by FastAPI) — useful for manually testing an endpoint
without needing the Flutter app running yet.

The SQLite database and generated invoice PDFs are created under
`data/` on first run (`data/vyapaarsaathi.db`, `data/invoices/`,
`data/uploads/`) — no manual DB setup step needed.

## 2. IMPORTANT — the speech-to-text model needs internet on first use

`faster-whisper` downloads its model checkpoint from Hugging Face
(~150MB for the default "base" model) the first time `transcribe_audio()`
runs, then caches it locally. **This was actually tested during
development and the download domain (`huggingface.co`) was blocked by
the dev sandbox's network policy** — so while the *code* is verified
correct (the `WhisperModel(...)` call signature and `transcribe()`
return shape were checked against the installed library directly), the
actual download-and-transcribe path could not be end-to-end verified
here.

**Do this before the hackathon, not during it:** on the actual venue
machine, run once with internet access:

```bash
python3 -c "from faster_whisper import WhisperModel; WhisperModel('base', device='cpu', compute_type='int8')"
```

This forces the download while you still have time to fix a network
problem, instead of finding out live when a judge asks the app to
respond to a voice command.

## 3. What was actually tested (and what it returned)

Every endpoint was hit with real `curl` requests against a running
server during development. Selected results, included so "it's tested"
isn't just an unverifiable claim:

**Empty database (fresh install) — nothing errors, everything returns a
sane empty/zero state:**

```
GET /api/v1/transactions          -> [] (200)
GET /api/v1/credit-score          -> {"score":0,"breakdown":{"consistency":0,"diversity":0,"avg_daily_income":0.0}} (200)
GET /api/v1/analytics/heatmap     -> {"days":[]} (200)
```

**Capturing a real synthetic UPI screenshot (image containing "Rs 350
Paid") via OCR:**

```
POST /api/v1/transactions/capture -> confidence: 100, amount: 350.0
```

A version of the same test using the ₹ symbol instead of "Rs" text
came back at **confidence 66, not 100** — Tesseract commonly misreads
the ₹ glyph as a stray digit fused onto the amount. This is a real,
observed OCR limitation (see the comment block in `ai_models.py`), not
a hypothetical — expect UPI apps that render ₹ as a glyph (most of
them) to score lower confidence than ones showing "Rs." as text.

**Customer verification lifecycle** (auto-created during a capture with
a `customer_name`, since there's no dedicated create-customer endpoint
in the given contract):

backend/
  config.py               # centralized settings (thresholds, weights, paths)
  database.py              # SQLAlchemy models (TransactionRecord, CustomerRecord) + SQLite session
  ai_models.py              # real OCR (Tesseract) + real ASR (faster-whisper) — honesty notes inline
  transaction_pipeline.py    # orchestrates capture: decode -> OCR/ASR -> persist -> respond
  credit_scorer.py            # heuristic scoring over stored transactions
  analytics.py                 # heatmap aggregation (income/expense by day)
  gst_generator.py              # real PDF generation via reportlab
  main.py                        # FastAPI app, all 6 endpoints, request/response shapes
  data/                            # created at runtime: SQLite DB, generated PDFs, temp audio
```

Every response shape in `main.py` has an inline comment noting exactly
which Flutter model (`Transaction.fromJson`, `CreditScore.fromJson`,
etc.) it's contractually matched against — if you change a JSON key
here, grep the frontend for that comment to find what breaks.

## 4. Known limitations (read before pitching "on-device AI")

- **No trained vision model.** Amount detection is real OCR + regex
  heuristics, not a UPI-screen/cash-note classifier. It works
  reasonably on a clean payment-success screenshot; it cannot read an
  amount off a photo of cash notes at all (no text to OCR). If "AI
  detects your cash and UPI transactions" is part of the pitch, be
  ready to explain this scope honestly if asked how it works.

- **No trained category classifier.** Category is either voice-tagged
  (keyword-matched from a real transcript) or defaults to "other" —
  never inferred from the image itself.

- **Income vs. expense classification is a category-based heuristic**
  (`transaction_pipeline._infer_transaction_type`), assumed rather than
  explicitly stated by the user at capture time. A capture-screen
  income/expense toggle would remove this ambiguity entirely and is
  the recommended fix if misclassification shows up in testing.

- **Credit score is a transparent heuristic formula** (consistency +
  diversity + income, weighted — see `credit_scorer.py`), not a
  trained credit-risk model. Legitimate as an MVP signal; shouldn't be
  described to judges as ML-derived risk scoring.

- **"Download Credit Report" (frontend) reuses this same
  `/gst/invoice` endpoint** with a dummy line item — the PDF that comes
  back looks like an invoice, not a purpose-built report, because
  that's genuinely what gets rendered. See `gst_generator.py`'s
  module docstring.

- **GSTIN is a placeholder string** (`PENDING-GSTIN-REGISTRATION`) —
  replace `business_gstin_placeholder` in `config.py` with a real
  GSTIN before any invoice is used for an actual filing.
